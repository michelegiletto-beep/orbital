The Orbital 0.3 Mission Simulation Hub provides a dark English workspace shell with module navigation, keyboard shortcuts, command search, responsive layouts and a shared multi spacecraft flight state. Numerical analysis, local advanced mission execution and replay run in dedicated web workers. Graphics use local Earth imagery and independent Three.js resource lifecycles.

Orbital separates rendering, simulation, protocol, identity and audit. The kernel has no DOM, network, wall clock or randomness. States and commands are serializable. The browser previews maneuvers with the same kernel used by the server. Execution is server-authoritative when connected. A synthetic exercise requires no network after local assets load. No service worker cache is implemented; initial loading requires a local server.

Internal units are km, seconds and kg. Burn inputs use meters per second and are converted at the kernel boundary. Acceleration is −μr divided by the cube of distance. The Earth model has μ = 398600.4418 km³·s⁻² and radius 6371 km. RK4 integrates the two-body problem at a fixed 2 s step. Circular velocity, vis viva and the ellipse half-period define the analytical reference transfer. The rocket equation with a 320 s specific impulse determines burn mass loss.

The legacy two body transfer exercise omits atmospheric drag, J2, third bodies, radiation pressure, continuous thrust and attitude control. Its preview shows osculating elements. Prograde follows instantaneous velocity. Apogee detection uses the radial speed zero crossing with at most one integration step of delay. Transfer assessment requires both apsides within tolerance and eccentricity below 0.003. Legacy inspection and separation retain their linear circular relative motion executor. These educational models remain explicitly distinct from the nonlinear advanced mission engine.

The advanced flight engine propagates ECI states with central gravity, optional J2, engineering drag, impulses and finite thrust. The advanced mission layer adds client scenario snapshots, relative RTN measurements, ordered holds, bounded guidance, scalar roll synchronization, capture criteria, abort and localized disposal entry events. Docking, recovery and deorbiting launch through this layer. It reuses the inertial integration and mass accounting rather than the legacy linear proximity equations. See docs/flight-dynamics.md for equations, reference frames and model limits.

Replay applies initial state and ordered commands with sequence and timestamp validation. It is bit-identical within the same runtime. JavaScript transcendental functions do not guarantee binary identity across CPUs, browsers and runtimes. Exports include model version. A future Rust migration requires vector fixtures and numerical specification before claiming cross-platform determinism.

Ordinary command bodies are limited to 16 KiB. Library and generic flight archive bodies have a 4 MiB bound. Legacy sessions allow 10000 commands. Advanced mission journals allow 2000 commands and 24 hours of simulated time. Mutations are serialized per resource; advanced command envelopes include the expected sequence so concurrent writers cannot silently double apply a maneuver. The service uses one API replica with a local persistent volume. Multi replica authority, relational storage and operational retention administration are not implemented.

Advanced mission creation resolves a mission identifier and revision from the verified tenant library. The persisted record binds that mission snapshot, canonical scenario, command journal, recomputed report and authorization resource to a signed audit receipt. Restore verifies the newest matching receipt and reconstructs the session by replay. A missing committed record, altered metadata or an older signed file fails closed. The list endpoint verifies records under the same resource lock and exposes only authorized runs. Later library edits do not change an existing mission snapshot.

Legacy session persistence now binds the authorization resource and optional orbital mission snapshot as well as the numerical session. Existing local 0.2 records can be read only when signed audit identity and the fixed local policy establish ownership. The next accepted mutation writes the stronger record format without rewriting prior audit events. Production legacy records require a verified migration because unsigned tenant metadata cannot establish ownership. Library reads, updates and deliveries share one integrity check, including revision reset and missing file detection.

Client collections are editorial groupings within a tenant, not independent security domains. Identity, tenant, clearance, compartment and owner checks remain server responsibilities. An offline package contains one selected client collection and device calculations; it does not contain a federated identity service or a signed server authority. A packaged public key must be trusted through a separate channel.

The future data model includes tenant, session, mission, event, competency_result and audit_receipt. PostgreSQL is a candidate authority before multi replica operation, with optional time series and cache services. The current implementation uses REST and a read only legacy session WebSocket stream. Infrastructure templates describe deployment intent and do not establish an exercised production environment.
