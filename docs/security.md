Orbital 0.3 is executable engineering training software for synthetic scenarios. Implemented application controls, deployment controls and formal assessment remain distinct. No NIST, CMMC, FedRAMP, IL4, IL5, STIG, ASVS or FIPS certification is claimed. Operational flight use and classified information handling have not been qualified.

The API validates RS256 or ES256 JWT signatures, issuer, audience, expiry and a fifteen minute maximum token age. Access requires an amr claim containing mfa. Roles include operator, designer, instructor and auditor. ABAC checks tenant, owner, clearance and compartments. A designer can update tenant library content and export client deliveries. An operator can mutate an owned run; an instructor can review authorized tenant runs. Auditors cannot operate vehicles even when also assigned operator. Tokens missing mandatory attributes are rejected. Clearance and compartment checks are application labels, not an accredited MLS system.

The browser uses Authorization Code with PKCE S256, cookie bound state and ID token nonce validation. Tokens remain server side. The browser receives a random HttpOnly Secure SameSite Lax handle with absolute and idle fifteen minute limits. Cookie authenticated POST requests require the configured Origin, and any supplied foreign Origin is rejected. Login transactions expire after five minutes. HTTPS provider endpoints are explicitly configured. Smart cards, CAC, PIV and SAML are delegated to the institutional identity provider and need perimeter specific testing. Active revocation of previously accepted tokens is not implemented; short lifetimes bound exposure.

The audit chain uses SHA256 and ECDSA P256 signatures. Startup verifies the chain. Current session receipts bind numerical state, authorization resource and any retained orbital mission snapshot. Advanced mission records bind the library snapshot, canonical scenario, ordered journal, computed assessment and resource. Retrieval requires the newest matching receipt, so an older valid signed file does not silently roll back a run. Missing committed mission records fail closed. Rejected commands do not create successful state changes or assessments. Commands also require the expected journal sequence and are serialized per run.

Library reads, updates and delivery exports share the same integrity check. A revision reset, modified content or missing file after a signed commit is rejected. Deliveries cannot sign a library that ordinary reads reject. Result creation uses source mission identity and authoritative numerical evaluation; caller labels cannot move a grade to another client or mission. The idempotent result path verifies the existing signed record before returning it.

Legacy local 0.2 session records are accepted only when their audit subject proves the fixed local operator identity and their resource exactly matches the local tenant, owner, classification and training compartment. The next accepted command upgrades the persisted binding without rewriting prior audit events. Production legacy records fail closed pending verified migration because tenant ownership cannot be established from unsigned metadata. Administrators must not bypass an integrity failure by deleting audit history or renaming a record.

Each audit append is flushed, and export includes the public key. Files are tamper evident rather than immutable against an administrator holding both data and key. Valid tail truncation still requires an external checkpoint for detection. WORM storage, external digest anchors, nonexportable keys, rotation and institutional retention require deployment work. A command is audited before atomic state persistence, so a crash can leave an accepted record without the updated file. The subsequent newest receipt check fails closed. Authoritative recovery needs operational reconciliation with verified backups; there is no automatic repair that invents a missing state.

Client collections group exercise content within one tenant. They do not establish independent customer authorization boundaries. Cross organization isolation depends on authenticated tenant identity and policy. Advanced records use tenant scoped storage and audit namespaces. Offline client delivery contains only the selected collection but provides device calculation rather than a federated security perimeter. Do not place private customer records in a public source or demonstration package.

Development binds only to loopback. Production refuses to start without identity configuration and a preprovisioned audit key. Assets use no CDN, remote fonts or analytics. OpenTelemetry export is disabled by default and requires both an endpoint and OTEL_EGRESS_APPROVED=true. The operator explicitly initiates AAR export. Deployment must terminate TLS using a validated module required by the customer, encrypt volumes and provide perimeter-local secrets, network policy and backups. Using recognized algorithms is not FIPS 140-3 cryptographic module validation.

Publication packaging rejects traversal, drive paths, alternate data streams, reserved device names, ambiguous paths and duplicate extraction targets. Credential filenames and recognizable private key or access token material fail packaging checks. Source packaging uses selected directories and excludes local data, dependencies, temporary output and generated screenshots. These checks supplement a human review; they cannot recognize every possible confidential value. Offline manifests bind file hashes and a detached signature, but the recipient must establish public key trust through an independent channel. The SBOM and third party notices describe included dependencies; they do not constitute a security accreditation.

Threats considered include malformed commands, concurrent mutation, cross tenant access, invalid tokens, audit modification, rollback, result relabeling, unsafe publication content and vulnerable dependencies. Implemented mitigations include validation, per resource serialization, expected sequences, resource authorization, algorithm allowlists, signed snapshots, newest receipt checks and lockfile scanning. Incident detection, distributed rate limiting, continuous revocation, redundant availability, denied access audit and external key custody remain future work. POSIX modes require equivalent Windows ACLs and are not OS isolation.

The initial mapping links AC and IA to identity, AU to signed records, SC to TLS and network boundaries, CM and SA to the lockfile and inventory, and CP to backup procedures. NIST SP 800-171 and CMMC need additional organizational and operational evidence. The requested FedRAMP baseline and any IL target must be settled in the acquisition context before assessment. DISA STIG applies to operating systems, clusters and environment configuration as well. OWASP ASVS requires full-surface and connected-provider verification.
